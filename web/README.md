# web

Веб-интерфейс двух ролей: кабинет клиента (`/cabinet`) и рабочее место аналитика (`/bank`).
React 19 + Vite + TypeScript, обычный CSS, без UI-фреймворка и state manager. Типы API
генерирует `openapi-typescript` из `../api/*.yaml`, запросы идут через `openapi-fetch`.
В runtime нет Node-сервера: статику отдаёт nginx (`deploy/docker/web.Dockerfile`).

## Запуск

Нужен Node.js 22.12+ (или 20.19+). Из корня репозитория:

```sh
make web-install
make web-mock   # без backend: встроенный мок контрактов, http://localhost:5173
make web-dev    # с backend: /api проксируется на gateway (make gateway-up)
make web-up     # production-сборка в Docker, http://localhost:3000
```

`make web-dev` проксирует `/api` на gateway `http://127.0.0.1:${GATEWAY_PORT}` из
корневого `.env` (другой адрес — `WEB_API_PROXY`, например `http://127.0.0.1:3000`,
чтобы ходить через уже запущенный web-контейнер). В Docker nginx web-контейнера сам
маршрутизирует `/api/auth`, `/api/client`, `/api/backoffice` на `auth`,
`client-service`, `bank-service` внутри compose-сети.

## С настоящим backend

```sh
make infra-up auth-up auth-dev-seed client-up scoring-up bureau-up bank-up
make web-up     # http://localhost:3000
```

Учётки создаёт `make auth-dev-seed`: `client@smart-credit.test`,
`analyst@smart-credit.test`, `admin@smart-credit.test`; пароли — `AUTH_DEV_*` в
локальном `.env`. Каталог продуктов приходит в client-service из `bank.events`.
Каталог берётся из продуктов и правил `services/bank-service/seeds/demo.sql`.
Демо-дела из того же seed не имеют заявок в `client_db`: client-service отмечает их
события как обработанные и пропускает, поэтому полный `make bank-demo-seed` (его
запускает `make demo-up`) можно использовать вместе с клиентом.

Проверено на стенде (продукт `SME_CASHFLOW_V2`): ООО и ИП на патенте от профиля до
выдачи — черновик с подсказками, пожелания к условиям, документы по плану банка,
запрос патента и ответ на него, оценка денежного потока с вариантами, повторная
оценка, подтверждение варианта аналитиком, принятие, подпись и демо-выдача.

После принятия client-service продолжает отдавать принятую оферту в карточке, и
`POST /sign` берёт её `offer_id`. Копия в `localStorage` нужна только mock-режиму,
где mock-сервер оферту после принятия не возвращает.

Client-service отдаёт `form` только когда заданы сумма, срок и цель. До этого web
хранит введённые значения черновика в `localStorage`, чтобы они не пропадали после
перезагрузки.

## Профиль ИП/ООО, подсказки и оценка (контракт `api/assessment.yaml`)

- **Профиль v2** (`pages/client/Company.tsx`): форма бизнеса выбирается по длине ИНН
  организации; у ИП свои налоговые режимы (патент, НПД) и подписи, у ООО — ссылки
  на ГИР БО. Пустые суммы не отправляются нулями.
- **Черновик**: план требований `requirements_plan` от сервера — документы по этапам
  («до отправки», «для оценки», «по запросу») с периодом и подсказкой, где взять
  документ (`lib/external.ts`: ЛК ИП/юрлица на nalog.ru, ГИР БО, ЕГРЮЛ). Пожелания
  `assessment-input` (приоритет, комфортный платёж, минимальная сумма, срок)
  сохраняются в той же очереди автосохранения, что и форма.
- **Подсказки** (`lib/hints.ts`, тесты в `tests/hints.test.mjs`): по цифрам клиента
  и опубликованным порогам `docs/ASSESSMENT_V2.md` (покрытие платежа ×1,3, 12 месяцев
  деятельности) кабинет заранее показывает, что помогает и что мешает, и предлагает
  комфортную сумму одной кнопкой. Это не решение и не вероятность одобрения.
- **Решение для клиента** (`pages/client/AssessmentView.tsx`): «что повлияло» —
  расходящиеся полосы по публичным показателям оценки, график денежного потока
  (факт, прогноз, стресс, платежи), до трёх расчётных вариантов с запасом по потоку
  и сравнением с запросом, помощник `/help` (шаблон, если модель недоступна).
- **Аналитик** (`pages/bank/AssessmentPanel.tsx`): допуск и источники, факторы
  скоркарты v2, график, варианты с кнопкой «Предложить этот вариант» (заполняет
  решение точными условиями расчёта), «Пересчитать оценку», история поколений,
  продукты из `/backoffice/products`, запрос данных по `requirement_ids`.

## Документы и незаполненные поля

По ТЗ файл — демовложение: непустой файл до 5 MiB сохраняется вместе с именем,
типом и SHA-256. PDF, Excel и изображения не разбираются на реквизиты или суммы.
После загрузки интерфейс прямо сообщает, что поля нужно заполнить вручную.

В черновике отображается список недостающих полей и типов документов. Пока они
не заполнены, отправка недоступна и заявка остаётся черновиком. Профиль компании
проверяется перед сохранением; нулевая выручка/обязательства допустимы, пустые
поля не заменяются нулями.

В «Нужны данные» показаны запрос банка, ошибки рядом с полями и список недостающих
документов. Дробный/неположительный срок, пустая или нулевая сумма кредита не
отправляются. Нулевая прибыль и отрицательная прибыль допустимы.
Уже сохранённые документы берутся из карточки заявки, в том числе после
перезагрузки страницы. При ответе сервер передаёт полный набор вложений,
поэтому ранее приложенный бизнес-план не теряется при обновлении выписки.
После полного ответа показывается «Ответ отправлен», затем ожидается событие банка.

Проверки логики формы и выбора документов без запуска браузера (Node.js 22.12+):

```sh
npm --prefix web test
```

## Демо-режим

`make web-mock` включает `VITE_API_MOCK=true`: запросы обрабатывает
`src/mock/server.ts` в браузере, данные лежат в `localStorage`. Мок воспроизводит
конвейер с задержками (валидация → моки ЕГРЮЛ/БКИ → скоринг → решение) и пять исходов
по ИНН персон из `seed/personas.yaml`. Пароль у всех учёток — `demo`:

| Учётка | Что показывает |
|---|---|
| `bakery@demo.local` | профиль не заполнен → каталог → черновик → автооферта → подпись → выдача |
| `warehouse@demo.local` | заявка уже на ручном разборе (grade C) |
| `service@demo.local` | банк запрашивает данные, после ответа — оферта |
| `workshop@demo.local` | готовый черновик сверх лимита к выручке → аналитик делает контрпредложение |
| `closing@demo.local` | отказ по стоп-фактору: компания ликвидируется |
| `analyst@demo.local` | очередь, «Взять в работу», решение, резюме дела |

Правила мока — упрощённая копия правил bank-service для показа интерфейса, а не их
источник. В production-сборку мок не попадает. Кнопка «Сбросить демо-данные» в
верхней плашке возвращает исходное состояние.

## Устройство

- `src/api/http.ts` — клиенты `authApi`, `clientApi`, `bankApi`, `assessmentApi`. Access-токен
  только в памяти, refresh — HttpOnly cookie; при `401` один refresh и один повтор.
- `src/api/problem.ts` — `application/problem+json` → понятный текст ошибки.
- `src/components/Pipeline.tsx` — линия конвейера с текущим этапом заявки.
- `src/pages/client`, `src/pages/bank` — экраны ролей. Статусы, `allowed_actions`
  и `next_action` web берёт из ответа сервера и не вычисляет сам; состояние
  обновляется polling-ом, пока заявка в работе у банка.
- Деньги — целые копейки, ставка — basis points; ввод в рублях и процентах
  переводится без float. Все изменяющие POST отправляют `Idempotency-Key`,
  `PATCH`/`take`/`decision` — `If-Match` с версией.

После изменения `api/*.yaml` перегенерируйте типы: `make web-gen`, затем
`npm --prefix web run typecheck`.
