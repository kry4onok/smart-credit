# Сиды профиля ИП/ООО и требований

Это общие тестовые данные контрактного этапа. Они не создают пользователей,
заявки или банковские решения и не вызывают внешние реестры.

## Что подключено

- `requirements-cases.json`: 16 сценариев профиля и ожидаемых результатов общего
  модуля требований. Go-пакет `profilefixtures` в этой папке предоставляет `Load()`;
  каждый вызов возвращает независимые значения с общими типами из `pkg/api/common`.
  Отсутствующая прибыль, известный ноль и убыток сохраняют разный смысл.
- `index.json`: примеры HTTP и их схемы; `invalid-*.json` намеренно невалидны.
- `application-submitted.textproto`: пример нового Kafka payload.
- `../personas.yaml`: две личности из профильных сценариев добавлены в штатный
  каталог `bureau-mocks`. Сценарии с разными налогами используют одну и ту же
  личность ИП либо ООО; это варианты входа, а не 16 отдельных компаний.
  `GetCompanyProfile` возвращает `legal_form`. Налоговый режим из ЕГРЮЛ/ЕГРИП
  не выдумывается. Синтетические проверки банкротства, арбитража, исполнительных
  производств и связанных лиц для оценки v2 отдаёт `GetAssessmentSources`
  (`pkg/assessment/demo.go`); из этих сидов они не берутся.
- `../../services/bank-service/seeds/demo.sql`: продукт `SME_PROFILE_V2`, UUID
  `10000000-0000-4000-8000-000000000021`, политика `sme-profile-v1`.
  Продукт сидируется активным и публикуется клиентам: запрет активации из миграции
  банка `00004` снят миграцией `00006`. Основной продукт демо — `SME_CASHFLOW_V2`
  (политика `sme-profile-v2`) из того же seed.

Данные синтетические; совпадение ИНН с реальными субъектами возможно. Не используйте
их для обращений к реальным внешним источникам.

## Проверка и загрузка

Из корня репозитория:

```bash
make profile-seed-check
```

Команда проверяет чтение сценариев, сохранение значений, связь с каталогом моков
и тесты gRPC-сервера. Она **не проверяет выполнение матрицы требований**:
`expected` — ожидаемые результаты. Сам движок отдельно проверяется тестами `pkg/requirements`.

Для подготовленной локальной инфраструктуры и заполненного `.env`:

```bash
make bank-demo-seed
make bureau-up
```

`bank-demo-seed` сначала применяет банковские миграции, затем выполняет SQL-сид
с остановкой на ошибке. Нужен уже запущенный PostgreSQL. `bureau-up` пересобирает
мок-сервис и читает штатно примонтированный `seed/personas.yaml` при старте.
JSON-примеры не импортируются автоматически в клиентскую БД.

## Связь с клиентским backend и web

`personas.json` — синтетический каталог `scenario_id → bureau_inn/legal_form`.
Полные клиентские профили берутся из `requirements-cases.json` по scenario_id;
налоги и финансовые данные не копируются в ответ реестра. `LoadPersonas()`
проверяет полноту и согласованность связей. Web и его mock-режим эти ID не
используют.

Клиентский backend уже сохраняет v2, вычисляет требования черновика и передаёт
новые поля через существующий outbox. Он использует общую библиотеку
`pkg/requirements` из Backend-1. Миграция клиента — `00002_profile_requirements.sql`.
Банк уже принимает события профиля v2 и публикует требования после валидации.
Полный конвейер на `SME_PROFILE_V2` проверяет `scripts/profile_v2_docker_smoke.py`
([тестовые сценарии](../../docs/TEST_SCENARIOS.md)).

Моки первого этапа закрывают формы ИП/ООО, synthetic-профили, связь с реестровым
ответом и прежние сценарии unavailable/deadline/unknown INN. Демо-проверки
банкротства, арбитража, ФССП и связанных лиц описаны выше; здесь нет обращений
к реальным источникам и утверждений о реальных компаниях.
