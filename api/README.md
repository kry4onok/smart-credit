# Контракты Smart Credit

Контракты — исходные схемы обмена данными между командами. Сначала меняется схема,
затем генерируются типы/интерфейсы, затем меняется код producer и consumer.

## Файлы

- `common.yaml` — общий HTTP-словарь: деньги, роли, статусы, продукт, ошибки и заголовки.
- `auth.yaml`, `client.yaml`, `bank.yaml` — публичные HTTP API. Внешний URL: `/api` + путь из OpenAPI; nginx убирает `/api` перед сервисом.
- `codegen/*.yaml` — конфигурации `oapi-codegen` для общего Go-пакета и трёх HTTP-сервисов. Их `output` считается от корня репозитория.
- `../proto/common/common.proto` — общие protobuf-сообщения.
- `../proto/events/events.proto` — Kafka envelope и payload двух топиков.
- `../proto/scoring/scoring.proto`, `../proto/bureau/bureau.proto` — обязательные gRPC вызовы банка.
- `../proto/assistant/assistant.proto` — gRPC сервис объяснений и резюме для MVP.

## Как менять

1. Описать пользовательское действие и владельца данных. Решить, HTTP это, событие Kafka или gRPC. Между `client-service` и `bank-service` допускается только Kafka.
2. Указать вызывающего, запрос, успешный ответ, ошибки, роль и идемпотентность. Изменить схему и пример/сценарий в документации.
3. Показать diff архитектору и потребителю контракта до реализации. Для события проверить обе стороны и совместимость изменений.
4. Сгенерировать код и проверить сборку producer/consumer. Сгенерированный код не редактировать вручную.
5. Влить контракт в `main`; сервисные ветки подтягивают его и реализуют свою сторону.

Принят единый корневой Go module `github.com/alfabank-hackathon-2026/smart-credit` (совпадает с Git remote). Генерация из корня репозитория:

```bash
make gen
```

Сейчас `gen` вызывает `gen-openapi`; позже к нему добавится `gen-proto`.
`common` генерируется первым, поскольку сервисы импортируют его типы. Версия
`oapi-codegen` зафиксирована в `Makefile`. `buf` конфигурацию и генерацию
Go/Python protobuf добавим после согласования структуры Python-пакетов с
ML-командой.

Контракты меняются в этих же файлах. Добавление необязательного поля совместимо;
удаление или смену смысла поля согласовывают обе стороны до слияния. Для Kafka
`aggregate_version` — номер состояния конкретной заявки или каталога.

## Принятые решения

- Публичные API описаны OpenAPI 3.1.0. Проверена генерация типов и chi/strict-server с `oapi-codegen v2.8.0`; поведение конечного Go-кода ещё требует сборки в проекте.
- Один корневой Go module `github.com/alfabank-hackathon-2026/smart-credit`, чтобы сервисы делили `pkg/` и `proto/gen/go/`.
- HTTP суммы и protobuf суммы — `int64` копейки + `RUB`; процент — basis points; время — UTC.
- В HTTP денежная сумма ограничена точным целым диапазоном JavaScript (`±(2^53-1)` копеек); реальный продуктовый лимит намного ниже и проверяется отдельно.
- В HTTP `Idempotency-Key` нужен для создающих/состояние меняющих POST; `If-Match` защищает конкурирующее редактирование.
- Отсутствующие необязательные вложенные объекты **опускаются**, а не передаются `null`, чтобы Go-кодогенерация была предсказуемой.
- В Kafka полное публичное состояние заявки уходит одним типом события. Отдельных `OfferMade`/`InfoRequested` нет: эти данные вложены в `ApplicationPublicStatePublished`, поэтому проекция восстанавливается последним снимком.
- Event key = `aggregate_id`, для заявки это UUID, для каталога — строка `catalog`. Каталог имеет отдельную последовательность `aggregate_version`.
- Outbox relay публикует события одного `aggregate_id` в порядке версии: нельзя брать следующее событие, пока предыдущее не отмечено опубликованным. Это критично для команд `OfferAccepted`/`ContractSigned`, которые не являются полными снимками.
- В `bank.events` нет score, внутренних правил, комментариев аналитика и данных БКИ.
- Health routes обслуживаются напрямую сервисами и могут быть недоступны снаружи nginx.
- Состояние в браузере обновляется polling через GET.
- `assistant` вызывается только bank-service: резюме дела для аналитика и текст публичного объяснения решения. При таймауте используется шаблон; решение, score и условия оферты не меняются. Отдельного клиентского чата в текущем объёме нет.
- Для публичного объяснения bank-service вычисляет решение, затем вызывает `ExplainDecision` вне SQL-транзакции. Решение, текст (или шаблон) и outbox-событие сохраняются вместе с проверкой версии дела.
- У ручного решения внутренний `comment` остаётся в аудите; для отказа и контрпредложения аналитик вводит отдельный `public_reason`. В assistant уходит только эта безопасная причина и публичные коды, а не внутренний комментарий.
- `GET /client/applications/{application_id}` возвращает понятное название этапа и допустимые действия; `GET /backoffice/applications/{application_id}` возвращает активный запрос данных и текст, опубликованный клиенту. Web не вычисляет эти поля по локальным догадкам.
- `InfoField` в HTTP передаётся без префикса; одноимённые значения protobuf имеют префикс `INFO_FIELD_`. Adapter явно конвертирует их и отклоняет `UNSPECIFIED`.
- Генератор выдаёт `*multipart.Reader` для `POST /documents`; HTTP adapter ограничивает файл 5 MiB (с запасом на multipart-обёртку для тела), читает `document_type`, считает SHA-256 и записывает файл в volume.
- Ручная оферта обязана содержать `product_id`; это позволяет банку предложить другой продукт, сумму, срок и ставку. Публичная оферта несёт снимок названия и версии предложенного продукта.
- Для заявки используются фиксированные `PurposeTag` и `DocumentType`; пороги grades, коды причин и правила двух демо-продуктов зафиксированы в разделе 8 `TZ.md`. ML возвращает оценку риска, bank-service применяет правила и принимает решение.
- Токен обновления не ротируется при каждом refresh: БД хранит хеш, срок 7 дней, logout отзывает токен.
- Автоматического DLQ нет: consumer не подтверждает offset при необработанном событии, повторяет с ограниченной задержкой и выводит ошибку в логи/readiness. Сообщение нельзя молча пропустить.

## Проверки при реализации

1. Достаточны ли поля компании и формы для тестовых персон, особенно для `InfoProvided`? Дополнительные документы можно запросить уже после submit.
2. ML-1 фиксирует веса скоркарты и версии модели/признаков; Backend-1 проверяет соблюдение порогов и кодов причин из `TZ.md` на одинаковых входах.
3. При добавлении seed заполнить два продукта по правилам раздела 8 `TZ.md` и прогнать сценарии автооферты, ручного разбора, отказа и контрпредложения.
4. После появления `go.mod` прогнать `make gen` и сборку сгенерированных пакетов; сам факт успешной генерации не заменяет компиляцию.
