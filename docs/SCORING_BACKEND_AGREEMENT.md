# Scoring v1: контракт первого MVP для backend

Дата: 22.10.2026. ML-ветка: `feat/ml-scoring`.

**Решения со стороны ML зафиксированы.** По этому документу можно готовить данные, моки и банковский adapter. Обновление scoring protobuf, модель, Python-сервис и контрольные примеры выполняет ML; ниже указаны зависимости для backend. Scoring/bureau protobuf уже обновлены; generated Go/Python пакеты находятся в `proto/gen`. Контракт опубликован отдельно от реализации сервиса; его наличие само по себе не подтверждает готовность runtime.

## 1. Что делает scoring

`smartcredit.scoring.ScoringService/Score` оценивает **риск бизнеса**, возвращает `score` 0..1000, grade A–E и объяснения. Чем выше score, тем ниже риск. Это демонстрационный индекс, не вероятность дефолта.

Сумма, срок, продукт, цель и документы проверяются банком и не меняют borrower score v1. Банк принимает кредитное решение и формирует оферту. Расчёт платёжной нагрузки и альтернативных условий **не входит в первый MVP scoring**; дополнительные поля денежного потока сейчас не нужны.

Для ядра v1 достаточно шести показателей ниже. ИНН, название и UUID не являются признаками модели. Формула и веса принадлежат ML; backend не требуется реализовывать их повторно.

## 2. Данные: что заполнить сейчас

| Поле Features | Тип и единицы | Источник у банка | Правила |
|---|---|---|---|
| `revenue_12m` | Money, целые копейки, RUB | `company.revenue_12m` из сохранённого снимка заявки | ≥0; реальный 0 означает неприменимость модели |
| `profit_12m` | Money, целые копейки, RUB | `company.profit_12m` из того же снимка | Допускаются 0 и отрицательная прибыль |
| `total_debt` | Money, целые копейки, RUB | Успешный `GetCreditHistory` текущей попытки enrichment | ≥0; остаток задолженности, не месячный платёж |
| `company_age_months` | optional int32, полные месяцы | Банк вычисляет по `registered_at` из успешного `GetCompanyProfile` | ≥0; отсутствие даты не заменяется возрастом 0 |
| `overdue_count_12m` | optional int32 | Успешный `GetCreditHistory` текущей попытки | ≥0; число отдельных эпизодов просрочки в окне |
| `max_overdue_days` | optional int32, дни | Тот же ответ кредитной истории | ≥0; максимальный достигнутый DPD в том же окне |

**Единицы и периоды фиксированы:**

- Все денежные значения — копейки, `currency=RUB`, без float. Для совместимости с HTTP/JavaScript абсолютная сумма не больше `9007199254740991`; отрицательной может быть только прибыль.
- Банк один раз фиксирует `as_of_date` как UTC-дату начала попытки оценки и сохраняет её с попыткой. При повторе того же вычисления дата не меняется.
- Окно выручки, прибыли и просрочек: `(as_of_date минус 12 календарных месяцев; as_of_date]`. Для бизнеса моложе года берём фактические показатели внутри этого окна, без искусственного пересчёта на полный год. `total_debt` — остаток на `as_of_date`, не сумма задолженностей за год.
- Эпизод просрочки учитывается, если хотя бы один день просрочки попал в окно. Для `max_overdue_days` берём максимальную длительность, достигнутую в окне, включая продолжающийся старый эпизод. Значение может превышать 365 дней.
- Возраст: разница year/month минус один, если месячная годовщина регистрации ещё не наступила. Для годовщины день регистрации ограничивается последним днём целевого месяца. Дата регистрации в будущем — ошибка входа.
- `count=0, max_days>0` и `count>0, max_days=0` — противоречивые данные. Явные `0/0` означают отсутствие просрочек.

`obligations` не складывается с `total_debt` и не участвует в модели v1. `obligations`, `okved_group`, `requested_amount`, `requested_term_months`, `purpose_tag` сохраняются в protobuf для совместимости, но не обязательны для вычисления score. Их смысл и использование в остальных банковских операциях этот контракт не меняет.

**Пропуск ≠ ноль:** отсутствующий Money не создаём; для трёх scalar-показателей используем explicit presence. ML добавляет `optional` в scoring и bureau proto; backend явно устанавливает известные нули в bureau mock и сохраняет presence в adapter. Не собирать запрос из HTTP-карточки, где `COALESCE` уже превратил отсутствующие сведения БКИ в нули.

## 3. Запрос и примеры для подготовки профилей

Envelope остаётся прежним: `application_id` и `product_id` — UUID; `feature_schema_version` — строго `borrower-features-v1`; `features` — данные из раздела 2. Существование и допустимость продукта проверяет банк, scoring не обращается к каталогу.

Пример запроса в **ProtoJSON**; int64 представлены строками. Это описание gRPC-сообщения, не новый HTTP endpoint:

```json
{
  "applicationId": "c1000000-0000-4000-8000-000000000001",
  "productId": "11111111-1111-4111-8111-111111111111",
  "featureSchemaVersion": "borrower-features-v1",
  "features": {
    "revenue12m": {"amountKopecks": "1200000000", "currency": "RUB"},
    "profit12m": {"amountKopecks": "180000000", "currency": "RUB"},
    "totalDebt": {"amountKopecks": "300000000", "currency": "RUB"},
    "companyAgeMonths": 36,
    "overdueCount12m": 0,
    "maxOverdueDays": 0
  }
}
```

**Набор исходных профилей для моков и интеграции:** `as_of_date=2026-10-22`, `company_status=ACTIVE`, `revenue_12m=1200000000` копеек у всех, кроме явно указанного случая. Прибыль и долг в таблице также в копейках. Возраст вычисляется из даты регистрации по правилу выше. При прогоне этих fixtures backend использует зафиксированную дату из набора, а не дату системных часов; для обычной новой оценки действует дата начала попытки.

| Профиль | `registered_at` | `profit_12m` | `total_debt` | count / days | Ожидаемый результат scoring |
|---|---|---:|---:|---|---|
| `risk_a` | 2023-10-22 | 180000000 | 300000000 | 0 / 0 | ASSESSED, 938 / A |
| `risk_b` | 2023-10-22 | 60000000 | 1200000000 | 0 / 0 | ASSESSED, 700 / B |
| `risk_c` | 2025-10-22 | 60000000 | 1200000000 | 1 / 7 | ASSESSED, 510 / C |
| `risk_d` | 2025-10-22 | 30000000 | 1200000000 | 1 / 7 | ASSESSED, 472 / D |
| `risk_e` | 2026-04-22 | -120000000 | 2400000000 | 2 / 60 | ASSESSED, 55 / E |
| `zero_debt` | 2023-10-22 | 180000000 | 0 | 0 / 0 | ASSESSED, 975 / A |
| `score_zero` | 2026-10-01 | -120000000 | 2400000000 | 6 / 7 | ASSESSED, 0 / E; score присутствует |
| `zero_revenue` | 2023-10-22 | 0 | 0 | 0 / 0 | Выручка переопределена в 0: UNSUPPORTED_INPUT / ZERO_REVENUE, без score |
| `missing_debt` | 2023-10-22 | 180000000 | **поле опущено** | 0 / 0 | INSUFFICIENT_DATA / MISSING_VALUE, без score |
| `conflicting_overdue` | 2023-10-22 | 180000000 | 300000000 | 0 / 7 | UNSUPPORTED_INPUT / INCONSISTENT_OVERDUE, без score |

Это контрольные примеры по зафиксированной формуле, **не обучающая выборка**. Общий набор `seed/scoring/personas.json` поставляется с реализацией scoring; готовность runtime и результаты проверок фиксируются отдельно. Имена профилей не используются в вычислении; application UUID и синтетические ИНН можно назначить в общем seed. Product UUID в JSON — существующий demo-продукт, не зашитое в модель правило.

Для полного банковского пути также нужны два варианта: ошибка БКИ → manual review без подстановки нулей; профиль `risk_a` с `company_status=LIQUIDATED` → банковский отказ независимо от хорошего score, вызов scoring не требуется. Конкретные сумма/срок/документы остаются в банковских fixtures и проверяются по банковскому каталогу.

## 4. Ответ protobuf v1

Существующие номера полей и enum values сохранены. Scoring schema и generated пакеты обновлены. Backend обновляет consumer и bank OpenAPI для новых причин/метаданных.

| Поле ScoreResponse | Контракт v1 |
|---|---|
| `score = 1` | **optional int32**, 0..1000 |
| `grade = 2` | Существующий Grade; при отсутствии оценки — GRADE_UNSPECIFIED |
| `reasons = 3` | До трёх ненулевых причин: code, description, direction, абсолютный contribution |
| `model_version = 4` | `monotone-scorecard-v1` |
| `feature_schema_version = 5` | `borrower-features-v1` |
| `assessment_status = 6` | Новый enum: UNSPECIFIED=0, ASSESSED=1, INSUFFICIENT_DATA=2, UNSUPPORTED_INPUT=3; protobuf-префикс `ASSESSMENT_STATUS_` |
| `data_issues = 7` | repeated DataIssue: `string code=1`, `string field_path=2` |
| `factor_contributions = 8` | repeated FactorContribution: `string factor_name=1`, `int32 points=2`, `string description=3` |
| `baseline_score = 9` | int32, для v1 — 500 |
| `config_checksum = 10` | string, SHA-256 реально используемого конфигурационного артефакта, 64 lowercase hex |

У успешного ответа status=ASSESSED, score присутствует, grade соответствует числу, data_issues пуст. Полные вклады содержат четыре группы: `business_age`, `profit_margin`, `bureau_debt_load`, `payment_discipline`; `500 + sum(points) == score`. Points уже со знаком; в reasons знак задаётся direction. Reasons сортируются по `(-contribution, code)`, где code — имя без protobuf-префикса, и не являются полным разложением score.

При INSUFFICIENT_DATA / UNSUPPORTED_INPUT score **отсутствует**, grade=GRADE_UNSPECIFIED, reasons и factor_contributions пусты. Версии, checksum и baseline передаются. UNSPECIFIED status — нарушение контракта; банк не должен трактовать его как успешный score=0.

Data issues v1: `MISSING_VALUE` с путём отсутствующего поля; `ZERO_REVENUE` с `features.revenue_12m`; `INCONSISTENT_OVERDUE` с `features.max_overdue_days`. Для нескольких проблем — сортировка по `(field_path, code)`. Структурные ошибки проверяются первыми, затем пропуски, затем применимость; если одновременно нет долга и выручка 0, ответ INSUFFICIENT_DATA.

К существующему ReasonCode добавляются `REASON_CODE_HEALTHY_PROFIT_MARGIN=9`, `REASON_CODE_MANAGEABLE_BUREAU_DEBT=10`, `REASON_CODE_GOOD_PAYMENT_DISCIPLINE=11`. Старые значения не удаляются. `NO_OVERDUE` возможен только при явных `0/0`. Веса и формирование текстов reasons реализует ML.

## 5. Что должен делать банк

| Результат / ошибка | Действие первого MVP |
|---|---|
| ASSESSED, A=800..1000 или B=650..799 | Проверить банковские/product rules; автооферта допустима только при их выполнении |
| ASSESSED, C=500..649 или D=350..499 | MANUAL_REVIEW |
| ASSESSED, E=0..349 | REJECTED по действующей демонстрационной политике |
| INSUFFICIENT_DATA из-за выручки/прибыли клиента | NEEDS_INFO с конкретным полем; если клиентский путь запроса ещё не реализован — MANUAL_REVIEW |
| Недостаток/противоречие внешних сведений, реальная выручка 0 | MANUAL_REVIEW; отсутствие оценки не подменяется grade E |
| INVALID_ARGUMENT: неверная валюта, отрицательная выручка/долг/возраст/просрочка, некорректные UUID или структура | Без автоматического повтора; техническая причина в аудите, MANUAL_REVIEW |
| FAILED_PRECONDITION: неизвестная feature version | Без автоматического повтора; MANUAL_REVIEW и исправление совместимости |
| DEADLINE_EXCEEDED / UNAVAILABLE / INTERNAL | MANUAL_REVIEW с технической причиной; никакого запасного хорошего score |

Неполнота формы/документов, обязательные источники, company status, стоп-факторы, продукт, ставки и оферты принадлежат банковскому конвейеру. Хороший score не отменяет его проверок. Только модельные ASSESSED-результаты вставляются в score_results, где score NOT NULL. Отсутствие результата сохраняется как outcome попытки и в аудите.

**Актуальность:** при изменении данных или начале повторной проверки обязательного источника снять прежний score с позиции текущего. Сохранять input revision и attempt ID; поздний ответ старой попытки не может заменить новый. Карточка показывает только успешную оценку текущего входа; исторические результаты остаются историей. Обычная case.version не заменяет input revision, поскольку меняется также при назначении аналитика. Физическую схему хранения реализует backend; достаточно этих инвариантов, привязки сохранённого результата к делу/revision/attempt и явного outcome. Старую initial migration не переписывать.

Вместе с результатом сохраняются точный вход, дата оценки, версии, checksum, все вклады и data issues. GET карточки не пересчитывает score. Внутренние оценки и причины доступны банку; в `bank.events` и клиентскую карточку они не попадают. Клиенту банк передаёт публичное объяснение и условия.

## 6. Интеграция и владельцы

- **ML:** дельта scoring/bureau protobuf, модель/конфиг, Python gRPC, health, контейнер, контрольные данные, Python smoke и пример Go-вызова. Устаревшие ручные scores `demo-1` не воспроизводятся искусственно.
- **Backend:** данные из snapshots/enrichment с сохранением presence; расчёт возраста; bureau mock/adapter; вызов на этапе SCORING; банковские правила; сохранение актуального outcome, карточка и миграция.
- **Codegen:** ML добавляет общую генерацию пяти proto для Python/Go и фиксирует версии инструментов; backend использует generated пакеты и обновляет consumer. Generated код вручную не меняется. Существующий `make gen` дополняется protobuf-генерацией; Go module не понижается ради старого локального toolchain.
- **Runtime:** внутри Compose `scoring:50051`, локально `127.0.0.1:50051`; стандартный gRPC health, SERVING после проверки конфига. GPU, БД, Kafka и внешний модельный API scoring не нужны.
- **Вызов:** общий deadline 2 с; не более одного повтора UNAVAILABLE внутри этих же 2 с. Доменные результаты и ошибки схемы не повторяются автоматически. gRPC выполняется вне долгой SQL-транзакции; сохранение проверяет актуальность попытки и идемпотентно.
- **Логи:** application_id/attempt_id/trace_id, версии, длительность и outcome; без полного финансового запроса, документов и токенов.

Продуктовый каталог и его расхождения с SQL-seed исправляет backend в рамках своей работы; ML-контракт от конкретных названий/ставок/TTL не зависит. Ответ от backend нужен только при конкретном техническом блокере или несовместимости интерфейса, не для утверждения модели и её весов.

## 7. Минимальная совместная проверка

- [ ] Профили из раздела 3 дают одинаковый ожидаемый результат через Python и Go → Python.
- [ ] Успешный score=0 отличается от отсутствующего score; известные нули отличаются от пропусков.
- [ ] На одном деле проверены ASSESSED → INSUFFICIENT_DATA / UNSUPPORTED_INPUT / ошибка БКИ: старый score больше не текущий.
- [ ] Поздний ответ старой попытки не заменяет текущую оценку; повтор не создаёт двойное решение/оферту.
- [ ] Реальный результат scoring сохранён и возвращён карточкой; это не ручная запись demo-1.
- [ ] Хороший score не обходит hard-stop и продуктовые ограничения; недоступность scoring даёт безопасный банковский маршрут.

**Backend может готовить snapshots и моки по разделам 2–3 и использовать generated Go-пакеты. Модель и её веса согласования с backend не требуют. Дополнительные финансовые поля в первом MVP не нужны.**

Генерация всех пяти контрактов без ML-пакета: `uv run --no-project --python 3.12.12 scripts/generate_proto.py`; проверка без изменений: та же команда с `--check`. Python consumers добавляют `proto/gen/python` в `PYTHONPATH`; Go consumers импортируют `proto/gen/go/...`. Версии инструментов закреплены в `scripts/proto-tools.json` и metadata генератора. Обновить bureau producer и scoring consumer нужно вместе: старые proto3 producers не передают известный ноль, а старый score без assessment_status не считается результатом v1.
